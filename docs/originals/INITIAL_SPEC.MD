Functional and Architectural Specifications: Project "Photosphere"

1. General Vision and Project Goals

Project "Photosphere" (codename) aims to create a self-hosted multimedia (photo and video) storage, management, and search solution. The primary goal is to replicate and, in some ways, surpass the experience of commercial platforms (like Google Photos) while ensuring total control over personal data and drastically reducing cloud storage costs.

The fundamental paradigm of the system is based on "Edge-First" computing: all heavy processing (visual analysis, metadata extraction, hashing, artificial intelligence) is executed locally on the user's machine. The cloud is downgraded to purely passive storage and identity management, eliminating server-side computational costs.

2. Infrastructure and Cloud Constraints (GCP & Firebase)

The system relies on a specific hybrid infrastructure constrained to the following Google Cloud Platform (GCP) technologies to optimize operational costs:

Google Cloud Storage (Dual Bucket Setup):

Media Bucket (Storage Class: Archive): Strictly dedicated to the long-term storage of original media files (high-resolution photos and videos). Since this data has an extremely low overwrite and access frequency (WORM: Write Once, Read Many), the Archive class guarantees the lowest possible cost per gigabyte.

Data Bucket (Storage Class: Standard): Destined to host the relational JSON database and media thumbnails. These files require frequent access, rapid reads by the frontend, and continuous overwrites during ingestion, necessitating the Standard class.

Authentication and Authorization (Firebase):

Access to the User Interface (Frontend) is governed exclusively via Firebase Authentication.

Once logged in, the frontend receives a token that allows it to securely download images via Signed URLs and read the JSON files, ensuring Read-Only access to cloud data. This also enables controlled sharing of the library with other users (e.g., family members).

Local Authentication (Workload Identity):

The local ingestion application (the CLI) uses Workload Identity authentication (e.g., gcloud auth login) to authenticate against the GCP project. This grants the local application the necessary administrative privileges to upload media files and overwrite the JSON databases.

3. Media Processing Engine

The local ingestion pipeline begins with the physical analysis of files downloaded from mobile devices. The application must feature an engine capable of executing the following operations:

Media Typing and Discard Policy: The system must analyze each file to strictly categorize it into three macro-types: "Image", "Video", or "Extra File" (e.g., documents, unsupported formats, or metadata JSON files generated by Google Photos exports). Files classified as "Extra" are not permanently deleted to avoid accidental loss of auxiliary data; instead, they are isolated in a dedicated local folder (e.g., skipped/).

Native Metadata Extraction (EXIF/Video Metadata): For each valid file, the system must extract all contextual information embedded at the time of capture or recording. This includes: creation date and time, device/camera model, resolution (width and height), duration (for videos), and, notably, GPS spatial coordinates (latitude and longitude).

Thumbnail Generation (Thumbnailing): To ensure smooth performance on the frontend when scrolling through thousands of files, the system must generate low-resolution, compressed versions of each media item.

For images: resizing while maintaining the aspect ratio.

For videos: extraction of a keyframe (e.g., the first second of playback) saved as a compressed image.

Architectural note: These thumbnails will be uploaded to the Standard bucket.

4. Deduplication Engine (Visual Hashing as Primary Key)

To optimize Artificial Intelligence processing times and storage space, the system implements a radical deduplication logic based on visual content.

Visual Hash Calculation: Every image (or the keyframe of every video) is processed to generate an "Average Hash" or "Perceptual Hash" (pHash). This string represents the visual fingerprint of the file and is used as the Primary Key within the database.

Discarding Duplicates and Collision Handling: During ingestion, the system checks if the calculated hash already exists in the database.

If the hash is already present, the new file is discarded (and physically moved to the skipped/ folder along with unsupported files, keeping a record of the operation without polluting the cloud library).

This convention ensures that not only "bit-by-bit" identical files are ignored, but also similar images where minute variations (e.g., a single pixel change, burst shots) produce the same visual hash. The probability of collision is considered so low that it is an accepted and desired convention by the system to maximize speed, avoid scanning burst photos, and keep the library clean.

5. Artificial Intelligence and Localization Engine

If a media file is considered novel (the hash is not present in the database), it is passed to the AI module for content understanding.

Image Tagging: The local visual model analyzes the scene and extracts a list of precise labels (tags) identifying present objects, concepts, or subjects (e.g., "dog", "beach", "sunset").

Image Captioning: The model generates a coherent descriptive sentence that contextualizes the entire image or video.

Translation Flow (i18n): Since visual models operate natively and with higher accuracy in English, the system integrates a local translation module. The captions and tags generated in English are passed to this module and translated into the user's selected target language (e.g., Italian) before being archived, ensuring a fully localized interface and search experience.

6. Relational JSON Database Architecture

The system does not use a traditional database (SQL/NoSQL) running on a server. Instead, it relies on a "Serverless DB" model consisting of three structured tables as separate JSON files, uploaded to the Standard bucket. This guarantees lightweight operation, portability, and zero DB hosting costs.

The three core entities are linked via specific IDs:

Main Table (images.json):
This is the heart of the system. It contains a record for each processed media item and uses the file's Hash as a unique Primary Key. Each record includes the type (Image/Video), cloud storage paths (Original in Archive, Thumbnail in Standard), all extracted metadata (EXIF, GPS, dates), and "Foreign Keys" pointing to the descriptive tables: an array of Caption IDs and an array of Tag IDs.

Captions Table (captions.json):
A dictionary mapping the unique IDs (UUIDs) of captions to their respective translated texts.

Taxonomy Table (tags.json):
A dictionary collecting all unique system tags via ID (UUID). If 100 photos contain a "dog", the "dog" tag will exist only once in this file, optimizing the database size.

7. Cloud File Routing and Organization

While the JSON database provides exact indexing and pointing for every media item, the system includes configurable routing logic to keep the Archive bucket organized at a "virtual file system" level.
Using specific flags passed to the CLI, the user can dictate the structure of destination folders on the cloud:

Automatic Chronological Reorganization (Recommended): The system ignores the local folder structure and dynamically sorts files in the bucket based on the capture date extracted from metadata (e.g., creating a Year/Month/filename.jpg tree).

Maintain Current Structure: Files are uploaded by replicating the exact same directory tree present in the local source folder.

Fallback Strategy: If automatic reorganization is chosen but a file lacks valid time metadata (e.g., images downloaded from messaging apps), the system defaults to organizing the file in a directory based on the processing timestamp or an "unknown dates" folder.

The path generated by this logic is what will be permanently recorded in the cloud path field within images.json.

8. Final Operational Flow (CLI Pipeline)

When the user starts local processing, the application will execute operations in this exact sequence:

Scanning and Initial Cleanup: Analysis of the local directory. Auxiliary files (like export JSON metadata) or unsupported files are immediately isolated and physically moved to the local skipped/ folder.

Extraction and Calculation: For valid files, the system proceeds with metadata extraction, thumbnail generation, and Average/Perceptual Hash calculation.

Deduplication: Querying the local JSON database:

If the hash already exists as a key, the current file is considered a duplicate, is discarded from the main flow, and is also moved to the skipped/ folder.

If the hash does not exist, the system proceeds with AI processing (Tag + Caption in English) followed by Translation.

Routing: Determination of the destination cloud path based on routing flags (Chronological vs. Original Structure).

DB Population: Relational updating of tables in RAM, inserting the hash as the key for the images.json table, saving the newly calculated cloud path, and generating any new IDs for captions and tags.

Cloud Sync (Workload Identity):

Upload of new original files to the Archive bucket following routing rules.

Upload of new thumbnails to the Standard bucket.

Overwriting the three updated JSON files in the Standard bucket.

Completion: The process ends, leaving the staging directory clean (processed files are in the cloud, discarded ones are in skipped/). Web clients will display the updated content.
